# Audit Architetturale e Crittografico Zero-Knowledge (FASE 0)

> **Stato documento**: FASE 0 — Audit completo del codice reale (`server.ts`, `src/lib/*`, `templates/*`, `static/scripts/*`, `android-app/*`) rispetto al modello Zero-Knowledge v2.  
> **Regola applicata**: Dove il codice reale contraddice il `README.md`, fa fede il codice reale (tutte le discrepanze sono documentate nella §4).

---

## 1. Sintesi Esecutiva del Modello Attuale (v1) vs Target Zero-Knowledge (v2)

Nell'architettura attuale (**v1**), la cifratura è **interamente server-side**:
1. La chiave segreta dell'utente (`api_key`, stringa ASCII di 32 caratteri generata dal server in `POST /register` o scelta dall'utente come `custom_key`) viene trasmessa in chiaro al server a ogni login (`POST /login`) e mantenuta in chiaro nella RAM del processo Node (`SESSIONS: Map<string, { username, apiKey, expiresAt }>`).
2. Inoltre, quando l'utente crea una condivisione pubblica (`POST /api/shares/create`) o condivide un album con altri utenti (`POST /api/albums/share`), il server cifra `sess.apiKey` con un segreto locale del server (`user_media/.server-secret`) e la persiste su disco in `user_media/.shares.json` e `user_media/.album-shares.json`. Chiunque abbia accesso al filesystem del server o a un backup del volume può leggere `.server-secret`, decifrare le `apiKey` di tutti gli utenti con condivisioni attive e decifrare l'intero vault.
3. Il server riceve tutti i file in chiaro (anche salvandoli temporaneamente in chiaro su disco in `temp_uploads/`), vede tutti i nomi file originali, le estensioni, i MIME type, le date di scatto (`mtime`), gli EXIF/GPS (`.exif.json`), gli album (`.albums.json`), i preferiti (`.favorites.json`), gli hash SHA-256 del plaintext (`.hashes.json`), gli hash percettivi dHash/pHash delle immagini (`.phash.json`), genera miniature decodificando i pixel in RAM (`src/lib/thumbCache.ts`), estrae testo da PDF/Office in RAM (`src/lib/documentEngine.ts`) e crea archivi `.zip` **in chiaro** su disco (`temp_uploads/<taskId>.zip`).

Nell'architettura **Zero-Knowledge v2**, il server diventa un **blob store cieco autenticato**:
- Non riceve mai `accountKey`, passphrase, `root`, `kek`, `VK` (Vault Key), `metaKey`, `thumbKey`, `dedupKey`, `fkWrapKey` né `FK` (File Key).
- Riceve unicamente `authSecret = HKDF-SHA256(root, "photocloud/v2/auth")` per l'autenticazione, e conserva solo `Argon2id(authSecret, serverSalt)` (o `scrypt` di fallback).
- Tutti i file, le miniature (`320px` e `1280px`), i metadati per-blob e il catalogo album sono cifrati e autenticati interamente sui client (Web via WebCrypto + Argon2id WASM; Android via `javax.crypto` + `AndroidKeyStore` + Argon2id nativo/Kotlin) prima dell'upload.

## 3. Verifica Gestione Chiave al Login (Codice Reale)

L'analisi puntuale del codice reale conferma quanto segue:

1. **Registrazione (`server.ts:2209-2273`)**:
   - L'endpoint `POST /register` accetta `username` e opzionalmente `custom_key`.
   - Se `custom_key` non è fornita, il server chiama `generateApiKey(32)` (`src/lib/crypto.ts:34-41`), che genera 32 caratteri alfabetici/numerici.
   - Il server calcola `const hashed = hashKey(apiKey)` (`SHA-256(apiKey)` senza salt!) e aggiunge una riga `username:hashed` in `users.txt`.
   - Il server salva `SESSIONS.set(sid, { username, apiKey, expiresAt })` in RAM e invia al client il file `photocloud_auth_<username>.json` contenente `api_key` in chiaro.

2. **Login Web e Android (`server.ts:2286-2365`, `templates/login.html`, `MainActivity.kt:1324-1375`)**:
   - Sul Web (`templates/login.html`), l'utente seleziona il file `.json` (che viene inviato via `multipart/form-data` nel campo `auth_file`) oppure incolla manualmente `username` e `api_key`.
   - Quando viene caricato `auth_file`, il middleware `upload.single('auth_file')` scrive il file JSON (contenente `api_key` in chiaro) nella cartella `temp_uploads/upload_<timestamp>_<random>.tmp`, lo legge con `fs.readFileSync(req.file.path, 'utf-8')` e poi chiama `fs.unlinkSync(req.file.path)`.
   - Il server verifica `verifyKey(storedHash, apiKey)` e inserisce `apiKey` in chiaro nella mappa `SESSIONS` in memoria.
   - Su Android (`PhotoCloudApiClient.kt:475-525`), `loginWithKeyFile` carica il file `.json` via multipart a `POST /login`, riceve il cookie `photocloud_sid` e in `MainActivity.kt:922-943` salva l'intero file JSON in Base64 dentro `SharedPreferences` non cifrate (`saved_auth_key_b64`).

## 4. Verifica Keystore in `android-app/app` e Incoerenze tra `README.md` e Codice Reale

### 4.1 Esiste un keystore committato in `android-app/app`?
- **Verifica sul file tree**: L'ispezione di `/android-app`, `/android-app/app` e l'intera working tree conferma che **non c'è alcun file `.jks`, `.keystore`, `.p12` o `signing.properties` committato nel repository**. Il file `/.gitignore` (righe 19-25) ignora correttamente `*.jks`, `*.keystore`, `*.p12` e `android-app/signing.properties`.
- **Tuttavia, l'audit del codice ha rilevato due comportamenti critici nella gestione del keystore locale**:
  1. **`src/lib/persistentSigning.ts` (righe 410-413)**: La funzione `ensurePersistentLocalSigning()` (invocata da `npm run android:signing:setup` e durante la build release server-side) genera un keystore PKCS#12 in `~/.photocloud/release-signing.p12`, ma poi **scrive automaticamente `android-app/signing.properties` con le password in chiaro dentro la cartella del progetto** (`writeProtectedSigningProperties(projectPropsPath, createdCfg)`). Se un sviluppatore forza `git add -f` o impacchetta la directory `android-app/`, le credenziali e il path del keystore finiscono nel pacchetto.
  2. **`android-app/app/build.gradle.kts` (righe 190-245)**: Contrariamente a quanto dichiarato nel `README.md` (che afferma che il task `assembleRelease` fallisce se l'utente non fornisce le credenziali su uno dei 3 livelli), quando `assembleRelease` viene eseguito fuori da CI (`!isCiEnv`) senza credenziali configurate, lo script Gradle invoca silenziosamente `keytool -genkeypair` e auto-genera `~/.photocloud/release-signing.p12` e `~/.photocloud/signing.properties`.

### 4.2 Altre Incoerenze Rilevate tra `README.md` e Codice Reale
1. **Stack Frontend Web (`README.md:14` e `330-355` vs `server.ts`)**:
   - Il `README.md` dichiara che il frontend web è una SPA costruita con **React 19, Vite e Tailwind CSS 4** (`src/App.tsx`, `src/components/*`).
   - **Realtà del codice**: `server.ts` non monta mai Vite né serve la build di React; tutte le rotte web (`/`, `/trash`, `/login`, `/register`, `/map`, `/share/:token`) sono renderizzate lato server tramite template HTML monolitici (`src/lib/templateRenderer.ts`, `templates/base.html`, `templates/login.html`, `src/lib/sharePage.ts`, `src/lib/mapPage.ts`) accompagnati da script vanilla JS in `/static/scripts/*.js` (`gallery- selection.js`, `chunked-upload.js`, `instant-photo-editor.js`, `document-viewer.js`).
2. **Allineamento Versione Android (`server.ts:104` vs `android-app/app/build.gradle.kts:23-24`)**:
   - `android-app/app/build.gradle.kts` e `package.json` sono alla versione **`1.5.1` (`versionCode = 33`)**, ma il fallback hardcoded in `server.ts:104` riporta ancora `versionName: '1.4.1', versionCode: 31`, mentre gli APK precompilati nella cartella `/release/` sono fermi a `v1.0.0`–`v1.0.3`.
3. **Generatore Progetto Android Legacy (`src/lib/androidBuilder.ts:217-366`)**:
   - Quando `POST /api/android/build-release` esporta il sorgente Android in formato `.zip` e usa il generatore in `src/lib/androidBuilder.ts` (`generateMainActivityKt`), genera ancora una vecchia `MainActivity` basata su `WebView` che contiene codice crittografico legacy `PBKDF2WithHmacSHA256` (100.000 iterazioni) + `AES/CFB/NoPadding` (`decryptMedia`).
4. **Formato Cifratura nei Commenti e Docs (`README.md` vs `src/lib/crypto.ts`)**:
   - `src/lib/crypto.ts` supporta sia `PhotoCloud-GCM-v1\0` (header 18B + salt 16B + IV 12B + tag 16B = 62 byte di overhead) sia un fallback silenzioso a `AES-256-CFB` per qualsiasi file che non inizi con i 18 byte magic `PhotoCloud-GCM-v1\0`. Questo fallback silenzioso in `decryptFileAsync` (`src/lib/crypto.ts:198-219`) non autentica il ciphertext (malleabilità completa se un attaccante corrompe o sostituisce l'header magic di un file GCM). In v2 il formato `PCZK` v1 elimina qualsiasi fallback non autenticato.
